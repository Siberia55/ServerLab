# Конкурс грантов

Учебный сервер на Java 17 и Maven. Реализован прямой вызов методов с JSON-запросами и ответами. Данные хранятся только в памяти. Клиент — JUnit-тесты; `main`, HTTP, интерфейс и внешняя БД не предусмотрены заданием.

## Проверка

Установите JDK 17 или новее и Maven 3.9. Из каталога с `pom.xml` выполните:

```shell
mvn test
mvn package
```

Также можно открыть `pom.xml` в IntelliJ IDEA как Maven-проект и запустить `TestServer`. При первой сборке Maven потребуется скачать зависимости из Maven Central. На компьютере создания `mvn -o test` завершился успешно: 8 тестов, 0 ошибок и пропусков. Использован JDK 25 со сборкой под Java 17. Полная упаковка `mvn package` в автономном режиме недоступна из-за отсутствующих в локальном кэше зависимостей JAR-плагина; для нее нужен доступ к Maven Central.

## Создание сервера

```java
Server server = new Server(
    new BigDecimal("1000000.00"), // общий фонд
    new BigDecimal("3"),          // оценки <= 3 не финансируются
    Instant.parse("2030-01-01T00:00:00Z") // момент X
);
```

Класс: `academy.tochkavhoda.competition.server.Server`. Все обращения идут через этот класс. Конструктор с четвертым параметром `Clock` позволяет проверять момент X без ожидания. Неверная конфигурация приводит к `IllegalArgumentException`, null-параметры — к `NullPointerException`.

Каждый экземпляр `Server` представляет отдельный конкурс с одной общей для его сервисов базой в памяти. Перезапуск или создание другого экземпляра не восстанавливает данные. Вместо глобального singleton база имеет единственный экземпляр в пределах конкурса: это сохраняет изоляцию конкурсов и тестов.

## Протокол

Все методы возвращают `ServerResponse` с геттерами `getResponseCode()` и `getResponseData()`. Код 200 означает успех; данные — JSON. Пустой успешный ответ — `{}`. Код 400 означает ошибку; данные содержат только `{"error":"Описание ошибки"}`. Ошибки пользовательских запросов возвращаются ответом, а не исключением.

Регистрация не выполняет вход автоматически. После нее нужен `login`; он возвращает `{"token":"UUID"}`. Каждый вход создает новый токен. Несколько токенов могут работать одновременно. `logout` аннулирует предъявленный токен; `leave` удаляет аккаунт и все его токены. Логины уникальны среди обеих ролей.

| Метод | JSON-запрос / результат |
| --- | --- |
| `registerParticipant(json)` | `{"firstName":"Иван","lastName":"Иванов","company":"Старт","login":"start","password":"secret"}` → `{}` |
| `registerExpert(json)` | `{"firstName":"Анна","lastName":"Петрова","directions":["математика"],"login":"expert","password":"secret"}` → `{}` |
| `login(json)` | `{"login":"start","password":"secret"}` → `{"token":"..."}` |
| `logout(token)` | Без JSON; выход из сессии → `{}` |
| `leave(token)` | Без JSON; удаление аккаунта → `{}` |
| `addApplications(token,json)` | Участник: `{"applications":[{"title":"Проект","description":"Описание","directions":["математика"],"amount":50000}]}` → `{"applicationIds":["..."]}` |
| `cancelApplication(token,json)` | Участник: `{"applicationId":"..."}` → `{}` |
| `rate(token,json)` | Эксперт: `{"applicationId":"...","value":5}` → `{}`; повторный вызов заменяет оценку |
| `deleteRating(token,json)` | Эксперт: `{"applicationId":"..."}` → `{}`; удаляет только собственную оценку |
| `findApplications(token,json)` | Эксперт: `{"directions":["математика"]}` → `{"applications":[...]}` |
| `getRatedApplications(token)` | Эксперт: все заявки с его оценкой → `{"applications":[...]}` |
| `getResults(token)` | Любой зарегистрированный пользователь после X → `{"awards":[{"applicationId":"...","amount":50000,"average":4.5}],"remaining":950000}` |

Элемент `applications` содержит `id`, `participantId`, `title`, `description`, `directions`, `amount`, `average` и `ownRating` (null, если своей оценки нет). Для заявки без оценок `average` равен 0. Пароли и логины в списки заявок не попадают.

Одна заявка передается массивом из одного элемента, несколько — одним массивом. Пакет добавляется целиком: при ошибке в любом элементе не создается ни одна заявка. После создания заявку и регистрационные данные изменять нельзя. Участник отменяет только собственные заявки. При удалении участника исчезают его заявки и связанные оценки; при удалении эксперта — его оценки.

## Уточнения к ТЗ и валидация

ТЗ не задает некоторые детали. В этой реализации приняты следующие правила:

- Название фирмы без учета регистра определяет повторную регистрацию участника. Сочетание имени и фамилии без учета регистра определяет повторную регистрацию эксперта. Для учебной модели этого достаточно; различить однофамильцев по предоставленным ТЗ данным невозможно.
- Имя, фамилия, фирма, название и описание заявки не могут быть пустыми. Логин — от 3 символов; пароль — от 6 и не только пробелы. Пароль сравнивается точно, с учетом регистра и пробелов. Дополнительные требования к сложности не введены.
- Направления — непустые строки, приводятся к нижнему регистру и очищаются от крайних пробелов. Список направлений обязателен и непуст. Эксперт может оценивать заявку, если совпадает хотя бы одно направление.
- При поиске используется совпадение хотя бы одного указанного направления. Все запрашиваемые направления должны входить в компетенцию эксперта.
- Сумма заявки положительная, не более двух значащих знаков после запятой. Фонд неотрицательный с той же точностью. Деньги представлены `BigDecimal`. Порог — число от 0 до 5. Оценка — целое JSON-число 1–5; строки и дробные числа не принимаются.
- Время X задается в `Instant`. При времени строго меньше X разрешены изменения заявок и оценок. В X и позже добавление, отмена заявок, изменение и удаление оценок запрещены, чтобы сохранить состояние конкурса на момент подведения итогов.
- До X `getResults` возвращает ошибку. В X и позже итоги вычисляются при первом обращении к серверу до выполнения самого запроса и сохраняются. При отсутствии обращений данные не изменяются, поэтому фоновый таймер не требуется.
- Итоги сохраняются и после удаления аккаунтов. Удаление по-прежнему уничтожает их текущие заявки/оценки, но не пересчитывает уже завершенный конкурс. В итогах хранятся только идентификаторы выигравших заявок, суммы и средние баллы.
- Заявки без оценок не финансируются. При наличии оценок учитывается их арифметическое среднее. Сравнение средних и порога выполняется точно через суммы и количество оценок, без ошибки округления. Только отображаемое среднее округляется до 12 знаков.

Ранжирование: средний балл по убыванию → сумма заявки по возрастанию → случайный порядок при полном равенстве. Запрошенный грант выдается целиком, если хватает остатка фонда; слишком дорогая заявка пропускается. При среднем балле <= порога обработка прекращается. Остаток не распределяется. Порядок равных заявок фиксируется при первом подведении итогов.

## Структура

`Server → UserService / GrantService → CompetitionDao → CompetitionDaoImpl → Database`.

Пакеты находятся в `academy.tochkavhoda.competition`: `server`, `service`, `dto.request`, `dto.response`, `model`, `dao`, `daoimpl`, `database`, `exception`. DTO и модели представлены неизменяемыми Java records. `Services` собирает зависимости, `ServiceSupport` содержит общие проверки, обработку JSON и фиксацию итогов. Все операции двух сервисов синхронизированы на общем DAO, поэтому пакетные изменения и подведение итогов не пересекаются.

Восемь интеграционных JUnit-тестов обращаются только к публичному `Server` и `ServerResponse`. Они проверяют регистрацию, роли и сессии, некорректный JSON, атомарность пакета, направления, замену/удаление оценок, удаление связанных данных, дедлайн, ранжирование, пропуск дорогой заявки, порог, остаток фонда и стабильность случайных равенств.
